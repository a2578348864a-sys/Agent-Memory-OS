# 本地服务启动必须门禁关键持久化依赖

## 结论

端口监听、首页 200 或浅层健康检查只能证明 Web 进程活着，不能证明数据库等关键持久化依赖可用。本地服务应在启动前完成真实、低风险的依赖检查，失败时直接拒绝启动。

## 适用场景

本地 Next.js、Node.js 或其他服务依赖 SQLite、数据库、缓存或持久化文件，并且业务页面可能在依赖失效时继续返回静态外壳。

## 最小做法

1. 提供版本化的本地专用启动入口，并显式固定本地数据源。
2. 启动前检查持久化文件存在、非空且格式有效。
3. 通过正式客户端执行低风险真实查询；SQLite 额外执行 `PRAGMA quick_check`。
4. 只有全部检查通过后才启动 Web 进程。
5. 为缺失、空文件、格式错误和查询失败编写负向测试。
6. 保留生产启动入口与生产配置，不让本地兜底静默影响生产。
7. **被检查的库与真正传给客户端的库必须同一文件**：SQLite 的 DATABASE_URL 必须由「已验证的绝对 databasePath」生成（`file:` + 绝对路径），相对 URL（如 file:./dev.db）会被 Prisma 解析到生成目录/当前工作目录下的空库——检查通过却连空库；父进程遗留的错误 DATABASE_URL 必须被覆盖。
8. 启动失败只允许按任务书规则重试一次：使用 `$env:DATABASE_URL`（或等价注入）补齐缺失 env 后重试，避免无限制循环；重试仍失败则拒绝启动。

## 验证

demo-project 的旧进程在首页和 `/api/health` 均为 200 时，登录后的候选池接口仍返回 500；同一数据库经显式本地数据源探测得到 `quick_check=ok`、候选 9 条、任务 3 条。加入启动门禁后，负向测试、全量测试、类型检查、lint、生产构建、页面/API/静态资源检查均通过，数据库摘要保持不变。

## 不适用

完全无状态、没有数据库或持久化依赖的纯静态应用。

## 风险

直接运行底层框架命令仍可能绕过本地启动门禁，因此项目规则必须声明唯一入口。检查日志不能输出连接串、环境变量或密钥；生产环境不得静默回退到本地数据源。
- 相对 SQLite URL 是隐蔽空库来源：校验脚本与运行时各写一条 URL 往往会分叉（本地开发常见），必须用同一绝对路径生成并加「同文件」断言（含中文路径/真实仓库路径的用例）。
